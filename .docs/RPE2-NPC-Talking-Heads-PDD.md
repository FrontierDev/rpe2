# RPE2 NPC Talking Heads — Product Design Document

**Status:** Proposed  
**Repository:** `FrontierDev/rpe2`  
**Target branch:** `dev`  
**Scope:** Host-authored NPC speech, talking-head presentation, DM Helper speech cues, and controlled-NPC speech  

---

## 1. Summary

RPE2 needs a host-authoritative NPC speech system for active events.

When an NPC speaks, every RPE participant should receive a **talking-head popup** below the event unit portraits. The popup uses the same transient presentation queue as the existing event-widget ticker tape, but has a larger presentation designed for dialogue.

A talking head contains:

- the speaking EventUnit's portrait on the left;
- the NPC's name, coloured using that EventUnit's team colour;
- the NPC's raid marker icon, when present;
- the NPC's EventUnit ID;
- the spoken text on the right.

NPC speech has two authoring paths:

1. **Planned speech from the DM Helper.** The host may attach one or more speech cues to pending NPC actions. The cue is emitted immediately before the associated action begins executing/commits, preserving authored timing and ensuring the speech enters the shared ticker queue before combat-log messages generated by that action.
2. **Immediate speech while controlling an NPC.** When the host has taken control of a non-player EventUnit, the action-bar control chrome provides a Speak control. The host can enter dialogue and broadcast it immediately without consuming an action or altering combat state.

Talking-head messages are presentation events, not combat-log records and not persistent event state.

## 2. Current Architecture

### 2.1 The event widget already has the required speaker presentation data

`client/ui/widgets/widget_Event.lua` already renders EventUnit portraits and has direct access to:

- `eventUnit.eventID`;
- `eventUnit.name`;
- `eventUnit.team`;
- `eventUnit.raidMarker`;
- model/display/file data used by `UI.UnitPortrait`;
- the active event's team definitions through `Event.GetTeamColor()`.

The existing portrait implementation already uses `UI.UnitPortrait`, whose `SetUnit()` path supports the same EventUnit model/portrait data required for a talking head.

The talking-head system should resolve presentation from the current EventUnit on each receiving client rather than serializing name, colour, raid marker, and model data into every speech message.

### 2.2 The current ticker tape is implemented as a combat-log queue

`client/ui/widgets/widget_Event.lua` currently owns:

```lua
combatLogQueue = {}
currentCombatLogEntry = nil
combatLogTickerToken = 0
combatLogTransitionToken = 0
```

and the lifecycle:

```text
QueueCombatLogEntry()
    -> AdvanceCombatLogTicker()
    -> ShowCurrentCombatLogEntry()
    -> StartCombatLogTickerTimer()
    -> fade out
    -> next queued entry
```

The compact combat-log panel is currently:

- anchored below the portrait area;
- one entry visible at a time;
- shown for `COMBAT_LOG_TIME_VISIBLE` (currently 5 seconds);
- faded in/out;
- cleared when the event widget is hidden.

This is already the correct scheduling behaviour for talking heads. The required change is to make the queue a **generic transient event-widget presentation queue** with multiple presentation types rather than creating a second competing timer/queue.

### 2.3 Combat log history is semantically separate from the ticker

`client/client_CombatLog.lua` normalizes combat-log entries and queues them into the event widget. The combat-log history panel and DM Helper consume combat-log/history data separately.

NPC dialogue must reuse only the **transient ticker scheduling layer**.

NPC speech must not become a combat-log entry merely because it uses the same presentation queue.

### 2.4 The DM Helper already has an authorization lifecycle for planned NPC actions

The host-only DM Helper is built by:

- `client/ui/widgets/widget_Event_DMHelper.lua`;
- `client/ui/widgets/widget_Event_AutopilotHelper.lua`.

Autopilot pending actions have stable `actionId` values and explicit transitions such as:

```text
spell: pending -> authorized -> executing -> completed
movement: pending -> confirmed
```

`client/autopilot/Authorization.lua` invokes `Client.OnAutopilotPendingActionAuthorized()` after authorization succeeds and immediately before execution.

`client/autopilot/EmoteCues.lua` already demonstrates the intended extension point: an authored cue can be associated with the pending plan and published when an action is authorized or movement is confirmed.

NPC speech cues should follow the same lifecycle rather than introducing a separate planner or timing engine.

### 2.5 Controlled NPCs already have dedicated action-bar control chrome

`client/client_Event.lua` tracks:

```lua
Client.ControlledEventUnitId
```

and exposes the controlled EventUnit through the action-bar control context.

`client/ui/widgets/widget_ActionBar_Control.lua` already shows:

- `Controlling <marker> <name> (#<eventId>)`;
- a close/release-control button;
- the controlled NPC's spells.

This is the correct location for immediate host speech. A Speak control should be added to this controlled-NPC chrome rather than creating a separate floating DM window.

## 3. Goals

The system must:

1. Display NPC dialogue as a large talking-head popup directly below the event portraits.
2. Serialize talking heads with the existing ticker tape so only one transient event-widget message is visible at a time.
3. Preserve existing combat ticker behaviour and timing.
4. Display the speaking NPC's portrait, team-coloured name, raid marker, EventUnit ID, and spoken text.
5. Allow the host to author speech cues against pending DM Helper actions.
6. Allow more than one speech cue to be queued when required.
7. Emit planned speech immediately before the associated action executes/commits.
8. Allow immediate speech while the host is actively controlling an NPC.
9. Broadcast speech once to all participating RPE clients using the existing Comms system.
10. Validate on every receiver that network speech came from the active event host.
11. Resolve speaker presentation from the active EventUnit rather than trusting presentation metadata supplied over the network.
12. Keep speech presentation transient: no database/schema changes and no event-rejoin hydration requirement.
13. Ensure event end/widget teardown clears pending presentation state cleanly.

---

## 4. Non-Goals

This project does not implement:

- player talking heads;
- voice/audio playback or text-to-speech;
- lip synchronization or animated portrait speech;
- branching dialogue trees;
- dialogue choices;
- localization of authored dialogue;
- persistent dialogue history;
- adding speech to the combat log;
- replaying talking heads to players who join after the speech was emitted;
- synchronizing DM Helper draft text to clients;
- changing NPC AI/planner decisions based on dialogue;
- consuming an NPC action, resource, cooldown, or turn for speaking.

## 5. Presentation Model

### 5.1 Shared transient presentation queue

Refactor the event widget's current combat-log-only queue into a typed queue.

Proposed conceptual state:

```lua
presentationQueue = {}
currentPresentationEntry = nil
presentationTimerToken = 0
presentationTransitionToken = 0
```

Each entry has a presentation kind:

```lua
{
    kind = "combat-log",
    payload = normalizedCombatLogEntry,
}
```

or:

```lua
{
    kind = "npc-speech",
    payload = normalizedNpcSpeechEntry,
}
```

Public adapters remain explicit:

```lua
EventWidget:QueueCombatLogEntry(entry)
EventWidget:QueueNpcSpeechEntry(entry)
```

Both call one internal method, for example:

```lua
EventWidget:QueuePresentationEntry(kind, payload)
```

This prevents talking heads and combat ticker messages from overlapping or maintaining independent fade timers.

### 5.2 FIFO ordering

The shared queue is strict FIFO.

If the current visible item is a combat ticker entry and the host sends speech, the speech waits for that entry to finish.

If the current visible item is NPC speech and combat events arrive, those combat entries wait until the talking head finishes.

Speech does not pre-empt an already-visible ticker message.

For planned DM Helper speech, the cue is published immediately before the associated NPC action executes. This means the speech enters the FIFO before combat-log emissions caused by that action.

### 5.3 Existing combat-log presentation remains unchanged

`kind = "combat-log"` continues to use the existing:

- compact `combatLogPanel`;
- `BuildCombatLogDisplayText()` formatting;
- 5-second visibility duration;
- fade-in/fade-out behaviour.

The refactor must not change combat-log history, ticker text, or combat-log network behaviour.

### 5.4 Talking-head layout

Add a second presentation panel anchored at the same event-widget presentation origin currently used by the combat ticker.

Conceptual layout:

```text
                EVENT UNIT PORTRAITS

        +-------------------------------------------+
        | +----------+  {skull} Varos (#6)          |
        | |          |                               |
        | | PORTRAIT |  "You have come much         |
        | |          |   further than I expected."  |
        | +----------+                               |
        +-------------------------------------------+
```

The talking-head panel should be substantially larger than the combat ticker. Exact final dimensions may be tuned during implementation, but the target is approximately:

```text
width: 520-560
minimum height: ~96
portrait: 64-72 square
```

The text region must word-wrap.

The panel may expand vertically to a bounded maximum if the existing UI primitives make that clean; otherwise use a fixed height sized for normal dialogue and enforce a reasonable authored-text maximum.

### 5.5 Header identity

The header uses this order:

```text
<raid marker> <team-coloured name> (#<eventUnitId>)
```

Examples:

```text
{skull} Nexus Warden (#6)
{cross} Injured Scout (#12)
```

Requirements:

- the raid marker is omitted when the EventUnit has no marker;
- only the NPC name is team-coloured;
- the EventUnit ID remains neutral text;
- the name colour is resolved from `Event.GetTeamColor(eventState, eventUnit.team)`;
- the marker uses the existing `UI.Inline:RaidMarker()` helper.

### 5.6 Portrait

Use `UI.UnitPortrait` rather than duplicating model/texture resolution.

The talking-head portrait is presentation-only. It does not need:

- health/resource bars;
- cast icons;
- target indicators;
- turn-complete state.

It should reuse the EventUnit's normal portrait/model configuration and fallback behaviour.

A talking head is an explicit host-authored reveal. If the selected NPC is currently hidden, the speech presentation should still use the actual NPC identity/portrait rather than replacing it with the ordinary hidden-unit portrait treatment.

### 5.7 Duration

Combat-log entries retain the current fixed 5-second duration.

NPC speech should use a longer duration because the popup contains prose. Use an entry-specific duration calculated from text length, for example:

```text
base: 5 seconds
+ approximately 35 ms per character
clamp: 5 to 12 seconds
```

The exact constants can be tuned during implementation, but the queue scheduler must support per-entry duration rather than applying `COMBAT_LOG_TIME_VISIBLE` to every presentation type.

No user-facing ruleset setting is required in this phase.

## 6. NPC Speech Data Contract

Normalized speech entry:

```lua
{
    eventId = "event-id",
    speechId = "event-id:speech:17",
    speakerEventId = 6,
    text = "You have come much further than I expected.",
}
```

Do not serialize:

- speaker name;
- team colour;
- raid marker;
- portrait/model data.

Those values are resolved from the active EventUnit at display time.

### 6.1 Validation

Speech normalization rejects:

- inactive/mismatched event IDs;
- missing or invalid `speakerEventId`;
- speakers that do not resolve to an EventUnit;
- player EventUnits;
- empty/whitespace-only text;
- text above the implementation's bounded payload limit;
- duplicate `speechId` values already handled by the client.

The text is plain authored text. It must not be interpreted as Lua or executable markup.

WoW colour/texture escape sequences supplied in speech text should be stripped or escaped so authored dialogue cannot inject arbitrary UI formatting into the talking-head body.

## 7. Network Synchronization

### 7.1 New Comms operation

Add one new operation in:

```text
core/internal/comms/Operations.lua
```

using the next available opcode at implementation time:

```text
NPC_SPEECH
```

Handler:

```lua
Client:HandleNpcSpeech(arguments, sender, distribution, target, message)
```

Proposed compact payload:

```text
[1] eventId
[2] speechId
[3] speakerEventId
[4] text
```

### 7.2 Host-authoritative send path

Add a client module such as:

```text
client/client_NpcSpeech.lua
```

with the central API:

```lua
Client:EmitNpcSpeech(speakerEventId, text, options)
```

The method:

```text
Resolve active event
    -> verify local player is event host
    -> verify EventUnit exists and is not a player
    -> normalize text
    -> allocate speechId
    -> queue locally through HandleNpcSpeech(..., "LOCAL")
    -> broadcast NPC_SPEECH to PARTY/RAID
```

Like combat-log emission, host-local presentation should occur immediately rather than waiting for the add-on message to loop back.

The physical PARTY/RAID self-copy must therefore be ignored on the host to prevent duplicate talking heads.

### 7.3 Receiver trust rules

For PARTY/RAID network messages, `HandleNpcSpeech()` must verify that the transport sender is the active event host.

The receiver must not trust a payload field claiming that the sender is the host.

Validation:

```text
active event exists
payload eventId == active event.id
transport sender == active event.hostName
speakerEventId resolves locally
speaker is not a player EventUnit
speechId not already handled
text valid
```

Only then is the normalized speech entry added to the shared presentation queue.

### 7.4 Duplicate suppression

Maintain a small event-scoped set/ring of recently handled `speechId` values.

This provides deterministic duplicate suppression in addition to ignoring the host's physical self-copy.

The set is transient and is cleared when the event ends.

## 8. DM Helper Planned Speech

### 8.1 Behaviour

During an Autopilot event, the host may attach talking-head speech to a pending NPC action.

A cue belongs to **one action and one explicit NPC speaker**.

Multiple speech cues may be attached to one pending action. They are emitted in authored order and therefore enter the shared presentation queue in that same order.

Examples:

```text
Pending action: NPC #6 casts Shadow Bolt
  Speech 1 — #6: "Enough."
  Speech 2 — #6: "Now you die."
```

or for a marker movement involving multiple units:

```text
Pending movement: Skull group moves near Player A
  Speech 1 — #2: "Spread out!"
  Speech 2 — #3: "On me!"
```

### 8.2 Cue storage

Speech cues are runtime state attached to the current pending authorization plan, not database/event-definition state.

Proposed plan additions:

```lua
plan.talkingHeadCuesById = {
    [cueId] = {
        id = cueId,
        actionId = actionId,
        speakerEventId = eventId,
        text = text,
        order = serial,
        sent = false,
    },
}

plan.talkingHeadCueIdsByActionId = {
    [actionId] = { cueId1, cueId2 },
}
```

This allows:

- multiple lines per action;
- deterministic authored order;
- one explicit speaker per line;
- idempotent send state.

### 8.3 Valid speakers

For a spell action, the available speaker is the spell's `casterEventId`.

For a movement action, available speakers are the action's `expectedMemberEventIds` that resolve to active non-player EventUnits.

The UI must not allow arbitrary unrelated units to be attached to an action.

### 8.4 Trigger timing

For spell actions:

```text
authorization succeeds
    -> publish attached talking-head cues
    -> existing emote cue hook
    -> execute authorized NPC action
```

The key requirement is that the talking-head emission occurs **after authorization has succeeded but before action execution can emit combat-log entries**.

For movement actions:

```text
host confirms movement as Done
    -> publish attached talking-head cues
    -> existing movement/emote follow-up
```

If a batch of actions is authorized, each action's speech cues are emitted when that specific action passes through its normal authorization sequence. Do not bulk-publish every speech cue before the batch starts.

### 8.5 Failed/rejected/stale actions

Speech cues must not be emitted when an action is:

- rejected;
- stale;
- blocked and never authorized;
- failed before the authorization hook is reached.

Once a speech cue has been emitted, subsequent action failure does not retract the line.

### 8.6 Replanning

A replan may replace action IDs and targeting assumptions.

Do not automatically migrate talking-head cues from a stale/replaced plan to the new plan.

When a pending plan becomes stale:

- its speech cues become non-sendable;
- the DM Helper should stop presenting them as active cues;
- the host may re-author them against the new pending actions.

This matches the safety model of action-bound plan state.

### 8.7 DM Helper UI

Extend the existing Autopilot DM Helper rather than creating a separate window.

When a pending action row is selected, provide a **Talking Head** authoring section in the lower authoring area.

Controls:

```text
Speaker: [NPC dropdown]
Text:    [multiline text area]

[Add Speech Cue]
```

Below or adjacent to the composer, show the cues attached to the selected action in order:

```text
{skull} #6 Nexus Warden — "Enough."
{skull} #6 Nexus Warden — "Now you die."
```

Each cue supports:

- edit;
- delete;
- move up/down when more than one cue exists.

A small speech indicator should be visible on a pending action row when that action has one or more talking-head cues attached, analogous to the existing `[Emote]` cue indication used elsewhere.

The existing DM Helper action-authorisation controls remain unchanged.

## 9. Immediate Speech While Controlling an NPC

### 9.1 Entry point

Extend:

```text
client/ui/widgets/widget_ActionBar_Control.lua
```

When all of the following are true:

```text
active event
local player is the event host
Client.ControlledEventUnitId resolves
controlled unit is not a player EventUnit
```

show a **Speak** control alongside the controlled-unit chrome.

Do not show this control for normal player action bars.

### 9.2 Composer

Clicking Speak opens a compact anchored composer associated with the action bar.

Suggested layout:

```text
{skull} Nexus Warden (#6)
[ multiline dialogue text                         ]
[ Speak ] [ Cancel ]
```

The speaker is fixed to the currently controlled EventUnit and cannot be changed inside the composer.

`Speak` calls the same central API used by DM Helper cues:

```lua
Client:EmitNpcSpeech(controlledUnit.eventID, text, {
    source = "controlled-unit",
})
```

There must not be a second network/presentation implementation for this path.

### 9.3 Control changes

If control is released or moved to another EventUnit while the composer is open:

- close the current composer;
- discard its unsent draft;
- never silently send the draft as the newly controlled NPC.

Event end also closes the composer.

### 9.4 Gameplay impact

Immediate speech:

- does not consume an action;
- does not end a turn;
- does not trigger the global cooldown;
- does not modify resources;
- does not alter Autopilot planning;
- may be used regardless of whether the controlled NPC currently has a castable spell.

## 11. Event Lifecycle

### Event start

Initialize transient speech duplicate tracking and presentation state lazily.

### Event running

Host may emit speech through:

```text
DM Helper cue trigger
or
controlled NPC Speak composer
```

All participants enqueue the same normalized `npc-speech` presentation entry.

### Widget hide

The generic transient presentation queue is cleared, replacing the current combat-log-only clear behaviour.

### Event end

Clear:

- current presentation entry;
- queued presentation entries;
- talking-head panel state;
- recent speech IDs;
- controlled-NPC speech composer;
- pending-plan talking-head cue state with the Autopilot runtime.

### Rejoin / reload

Talking heads are transient and are not replayed.

A client that reloads while a talking head is visible simply misses the remainder of that line.

No rejoin snapshot schema changes are required.

---

## 12. Failure Handling

### Invalid speaker

If `speakerEventId` does not resolve to an NPC in the active event, ignore the speech entry.

### Non-host network sender

Ignore the message and optionally emit an `RPE INTERNAL` diagnostic.

### Event mismatch

Ignore the message.

### Empty text

Do not send.

### Duplicate speech

Ignore already-handled `speechId`.

### UI unavailable during startup/teardown

The receiver may validate the message, but should only queue it when the event widget is in a usable active-event state. Do not recreate an event widget during teardown solely to show dialogue.

### Queue burst

Do not create concurrent panels. Every valid entry remains FIFO. The existing queue semantics are the backpressure mechanism.

## 13. Diagnostics

Add lightweight `RPE INTERNAL` diagnostics for:

```text
npc speech emitted
npc speech received
npc speech rejected: sender-not-host
npc speech rejected: event-mismatch
npc speech rejected: speaker-unavailable
npc speech rejected: duplicate
DM Helper speech cue added/removed/emitted
```

Do not log full dialogue text by default; log `speechId`, speaker EventUnit ID, source, and text length.

This keeps diagnostics useful without flooding logs with authored prose.

## 15. Acceptance Criteria

The feature is complete when all of the following are true.

### Presentation

```text
An NPC speech message displays below the EventUnit portraits.

The talking-head popup is larger than the existing compact ticker tape.

The popup contains the NPC portrait on the left and speech text on the right.

The popup shows the NPC's team-coloured name.

The popup shows the NPC's raid marker when present.

The popup shows the NPC's EventUnit ID.

Only one transient ticker/talking-head presentation is visible at a time.

Combat ticker messages and talking heads preserve FIFO ordering.

Existing combat ticker appearance and combat-log history remain unchanged.
```

### Synchronization

```text
Speech authored by the host appears once on the host and once on each connected RPE client.

The host does not receive a duplicate from its physical addon-message self-copy.

A non-host client cannot cause NPC talking heads to appear by sending NPC_SPEECH directly.

A speech payload cannot spoof a different name, team colour, raid marker, or portrait because clients resolve those from EventUnit state.

Duplicate speech IDs do not create duplicate talking heads.
```

### DM Helper

```text
The host can attach talking-head speech to a pending NPC action.

A pending action visibly indicates that speech is attached.

Multiple speech cues on one action preserve authored order.

Spell-action speech is emitted after authorization succeeds and before execution-generated combat messages.

Movement speech is emitted when the host confirms the movement.

Rejected/stale/never-authorized actions do not emit their queued speech.

Replanning does not incorrectly attach old speech cues to new action IDs.
```

### Controlled NPC

```text
When the host controls an NPC, the action-bar control chrome offers a Speak control.

The host can enter text and immediately broadcast a talking head as that controlled NPC.

The Speak control is not shown for a normal player action bar.

Speech does not consume an action, resource, cooldown, or turn.

Changing/releasing control closes the composer and cannot accidentally send as another NPC.
```

### Lifecycle

```text
Event end clears queued speech and hides the talking-head panel.

/reload does not require speech-history recovery and does not corrupt the event state.

No Profile, Dataset, Event, or EventUnit schema version change is required.
```

## 16. Principal Architectural Decisions

**NPC speech is host-authoritative.** Clients display speech only when it originates from the active event host.

**Speaker identity is an EventUnit ID, not serialized presentation data.** Name, colour, marker, and portrait are resolved from the live event roster.

**Talking heads and combat ticker messages share one FIFO scheduler.** This guarantees that transient event-widget presentations never overlap.

**Combat log and dialogue remain separate semantic systems.** Reusing the ticker scheduler does not make dialogue a combat-log entry.

**Planned dialogue attaches to pending actions.** Existing authorization/confirmation transitions provide deterministic timing without adding another execution engine.

**Planned speech publishes before action-generated combat messages.** The shared FIFO therefore presents dialogue before the consequences of the action it introduces.

**Immediate controlled-NPC speech uses the same central emit path.** DM Helper speech and on-the-fly speech cannot diverge in validation, networking, or presentation.

**Speech is transient.** Drafts, visible talking heads, and handled speech IDs are runtime state only; no database or rejoin snapshot changes are required.
